# 문서 기반 RAG 실습 프로젝트: 유지보수 문서 검색 및 근거 기반 답변 시스템 구현

---

## 1. 목적 / 배경

사내 프로젝트를 운영하다 보면, 아키텍처 문서·배포 가이드·장애 대응 매뉴얼 등 다양한 운영 문서가 축적됩니다. 하지만 문서가 많아질수록 "지금 필요한 정보가 어떤 문서의 어디에 있는지" 찾기 어렵고, 신규 팀원이나 담당자 교체 시에는 더욱 비효율이 발생합니다.

이런 문제의식에서 출발하여, "운영 문서를 기반으로 질문하면 관련 내용을 자동으로 검색하고 근거를 바탕으로 답변해주는 시스템"을 RAG(Retrieval-Augmented Generation, 검색 기반 증강 생성) 방식으로 구현해보고자 했습니다. 단순히 AI에게 질문을 던지는 것이 아니라, 우리 팀의 실제 문서를 근거로 답변하게 하여 정확성과 신뢰성을 높이는 것이 핵심 목표였습니다.

이번 실습은 RAG의 개념과 동작 흐름을 직접 만들어보면서 체험하고, 향후 실제 사내 문서에 적용할 수 있는 기초를 마련하는 데 목적을 두었습니다.

---

## 2. GenAI 활용 내용 및 수행 내용

### Cursor 활용

프로젝트 전체 구현 과정에서 Cursor(AI 코딩 도구)를 활용하였습니다. 프로젝트의 목적, 사용할 기술, 만들 기능, 화면 구성, 폴더 구조 등을 상세하게 글로 정리하여 Cursor에 전달하고, 이를 바탕으로 코드를 자동 생성한 뒤 검토·수정하는 방식으로 개발을 진행했습니다.

### OpenAI API 활용

OpenAI API는 두 가지 용도로 사용하였습니다:

1. **문서를 숫자로 변환 (text-embedding-3-small 모델 사용)**: 문서를 작은 조각(chunk)으로 나눈 뒤, 각 조각을 숫자 배열(벡터)로 변환하여 ChromaDB에 저장합니다. 이렇게 하면 사용자의 질문과 의미가 비슷한 문서를 찾을 수 있습니다.

2. **답변 만들기 (Responses API, gpt-4.1-nano 모델 사용)**: 검색된 문서 조각을 AI에게 전달하여, 해당 근거만을 바탕으로 질문에 답변하도록 합니다. 근거가 부족한 경우에는 "문서에서 충분한 근거를 찾지 못했습니다"라고 솔직하게 응답하도록 설계했습니다.

### 구현 흐름

실제 구현된 RAG의 동작 흐름은 다음과 같습니다:

1. **문서 읽기**: `/docs` 폴더의 `.md`, `.txt` 파일을 읽어옵니다.
2. **문서 쪼개기 (Chunking)**: 문서를 500글자 단위로 나누며, 앞뒤 50글자를 겹치게 하여(overlap) 문맥이 끊기지 않도록 합니다. 각 조각에는 "어떤 파일에서 왔는지"(`source_file`)와 "몇 번째 조각인지"(`chunk_index`) 정보를 함께 저장합니다.
3. **숫자 변환 & 저장 (임베딩)**: 각 조각을 `text-embedding-3-small` 모델로 숫자 배열(벡터)로 변환하고, ChromaDB에 저장합니다. 저장된 데이터는 프로그램을 다시 실행해도 유지됩니다.
4. **비슷한 문서 찾기 (Retrieval)**: 사용자 질문도 같은 방식으로 숫자 배열로 변환한 후, ChromaDB에서 가장 비슷한 조각 3개를 찾습니다.
5. **답변 만들기 (Generation)**: 찾아낸 조각들을 OpenAI Responses API에 보내서, 그 근거를 바탕으로 답변을 만듭니다.

### 결과물

- **Streamlit 웹앱**: 사이드바에 프로젝트 설명, Reindex 버튼, 샘플 질문 3개를 배치하고, 메인 화면에 문서 현황, 질문 입력창, 답변 영역, 검색 근거 표시 영역을 구성했습니다.
- **샘플 문서 3종**: 시스템 아키텍처 문서, 배포 가이드, 장애 대응 매뉴얼을 작성하여 실습에 활용할 수 있도록 했습니다.
- **파일별 역할 분리**: `utils.py`(문서 읽기/쪼개기), `ingest.py`(문서 저장), `rag.py`(검색/답변), `app.py`(웹 화면)로 파일별 역할을 명확히 나누었습니다.

## 3. 시사점 / Lesson's Learned / 향후 계획

### 배운 점

- RAG의 핵심은 "관련 문서를 찾는 것(검색)"과 "찾은 문서를 바탕으로 답변을 만드는 것(생성)"을 나누는 데 있으며, 직접 만들어보니 그 흐름이 생각보다 명확하고 이해하기 쉬웠습니다.
- LangChain 같은 외부 도구 없이도 OpenAI API와 ChromaDB만으로 기본적인 RAG 동작을 충분히 구현할 수 있었습니다. 외부 도구를 사용하지 않은 덕분에 각 단계가 코드에서 직접 드러나, 초보자도 흐름을 따라가기 쉬운 구조가 되었습니다.
- Cursor를 활용한 AI 기반 개발은 반복적인 코드 작성 시간을 크게 줄여주었으며, 특히 원하는 기능을 상세하게 정리해서 전달할수록 결과물의 품질이 높아졌습니다.

### 아쉬운 점 / 한계

- 현재 문서 쪼개기가 단순 글자 수 기준이라, 의미 있는 단위가 아닌 곳에서 잘리는 경우가 있습니다.
- `.md`, `.txt` 파일만 지원하므로 PDF, Word 문서 등 실제 회사에서 많이 쓰이는 형식은 별도 처리가 필요합니다.
- 3개의 샘플 문서로만 테스트했기 때문에, 문서가 수십~수백 개일 때의 검색 품질과 속도는 추가 확인이 필요합니다.

### 향후 계획

- 실제 사내 프로젝트의 운영 문서(Confluence, Wiki 등)를 대상으로 적용해보고 검색 품질을 평가할 계획입니다.
- PDF 읽기, 문단 단위 쪼개기, 키워드 검색과 의미 검색 결합 등의 개선을 통해 실용성을 높이고자 합니다.
- 팀 내 문서 기반 질의응답 도구로 발전시켜, 신규 팀원이 합류하거나 장애 대응 시 활용하는 방안을 검토 중입니다.
- 실제 사내 문서에 적용할 때 필요한 보안 정책 및 데이터 관리 방안에 대한 검토가 추가로 필요합니다.
