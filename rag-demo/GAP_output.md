# 문서 기반 RAG 실습 프로젝트: 유지보수 문서 검색 및 근거 기반 답변 시스템 구현

---

## 1. 목적 / 배경

사내 프로젝트를 운영하다 보면, 아키텍처 문서·배포 가이드·장애 대응 매뉴얼 등 다양한 운영 문서가 축적됩니다. 하지만 문서가 많아질수록 "지금 필요한 정보가 어떤 문서의 어디에 있는지" 찾기 어렵고, 신규 팀원이나 담당자 교체 시에는 더욱 비효율이 발생합니다.

이런 문제의식에서 출발하여, "운영 문서를 기반으로 질문하면 관련 내용을 자동으로 검색하고 근거를 바탕으로 답변해주는 시스템"을 RAG(Retrieval-Augmented Generation) 방식으로 구현해보고자 했습니다. 단순히 LLM에 질문을 던지는 것이 아니라, 우리 팀의 실제 문서를 근거로 답변하게 하여 정확성과 신뢰성을 높이는 것이 핵심 목표였습니다.

이번 실습은 RAG의 개념과 구현 흐름을 직접 체험하고, 향후 실제 사내 문서에 적용할 수 있는 기초를 마련하는 데 목적을 두었습니다.

---

## 2. GenAI 활용 내용 및 수행 내용

### Cursor 활용

프로젝트 전체 구현 과정에서 Cursor를 활용하였습니다. 프로젝트의 목적, 기술 스택, 구현 기능, UI 요구사항, 폴더 구조 등을 상세하게 기술한 프롬프트를 작성하여 Cursor에 지시하고, 이를 바탕으로 코드를 생성·검토·수정하는 방식으로 개발을 진행했습니다.

### OpenAI API 활용

OpenAI API는 두 가지 용도로 사용하였습니다:

1. **문서 임베딩 (text-embedding-3-small)**: 문서를 chunk 단위로 분할한 후 각 chunk를 벡터로 변환하여 ChromaDB에 저장합니다. 이 벡터를 기반으로 사용자 질문과 문서 간의 의미적 유사도를 계산합니다.

2. **답변 생성 (Responses API, gpt-4.1-nano)**: 검색된 문서 chunk를 컨텍스트로 전달하여, 해당 근거만을 바탕으로 질문에 답변하도록 합니다. 근거가 부족한 경우에는 "문서에서 충분한 근거를 찾지 못했습니다"라고 응답하도록 시스템 프롬프트를 설계했습니다.

### 구현 흐름

실제 구현된 RAG 파이프라인은 다음과 같습니다:

1. **문서 로드**: `/docs` 폴더의 `.md`, `.txt` 파일을 읽어옵니다.
2. **Chunking**: 문서를 500자 단위로 분할하며, 50자의 overlap을 두어 문맥이 끊기지 않도록 합니다. 각 chunk에는 출처 파일명(`source_file`)과 순번(`chunk_index`)을 메타데이터로 부여합니다.
3. **임베딩 & 저장**: 각 chunk를 `text-embedding-3-small` 모델로 임베딩하고, 결과를 ChromaDB(로컬 영속 저장)에 저장합니다.
4. **검색 (Retrieval)**: 사용자 질문을 동일한 임베딩 모델로 벡터화한 후, ChromaDB에서 유사도 기준 상위 3개 chunk를 검색합니다.
5. **답변 생성 (Generation)**: 검색된 chunk를 OpenAI Responses API에 전달하여 근거 기반 답변을 생성합니다.

### 결과물

- **Streamlit 웹앱**: 사이드바에 프로젝트 설명, Reindex 버튼, 샘플 질문 3개를 배치하고, 메인 화면에 문서 현황, 질문 입력창, 답변 영역, 검색 근거 표시 영역을 구성했습니다.
- **샘플 문서 3종**: 시스템 아키텍처 문서, 배포 가이드, 장애 대응 매뉴얼을 작성하여 실습에 활용할 수 있도록 했습니다.
- **모듈화된 코드**: `utils.py`(문서 로딩/분할), `ingest.py`(인덱싱), `rag.py`(검색/답변), `app.py`(UI)로 역할을 명확히 분리했습니다.

## 3. 시사점 / Lesson's Learned / 향후 계획

### 배운 점

- RAG의 핵심은 "검색(Retrieval)"과 "생성(Generation)"의 분리에 있으며, 직접 구현해보니 그 흐름이 생각보다 명확하고 이해하기 쉬웠습니다.
- LangChain 같은 프레임워크 없이도 OpenAI API와 ChromaDB만으로 기본적인 RAG 파이프라인을 충분히 구현할 수 있었습니다. 프레임워크를 사용하지 않은 덕분에 각 단계가 코드에서 직접 드러나, 초보자도 흐름을 따라가기 쉬운 구조가 되었습니다.
- Cursor를 활용한 프롬프트 기반 개발은 반복적인 코드 작성 시간을 크게 줄여주었으며, 특히 상세한 요구사항을 체계적으로 정리하여 프롬프트로 전달할수록 결과물의 품질이 높아졌습니다.

### 아쉬운 점 / 한계

- 현재 chunk 분할이 단순 글자 수 기반이라, 의미 단위가 아닌 곳에서 잘리는 경우가 있습니다.
- `.md`, `.txt` 파일만 지원하므로 PDF, DOCX 등 실제 사내에서 많이 쓰이는 형식은 별도 처리가 필요합니다.
- 소수의 샘플 문서로만 테스트했기 때문에, 대규모 문서에서의 검색 품질과 성능은 추가 검증이 필요합니다.

### 향후 계획

- 실제 사내 프로젝트의 운영 문서(Confluence, Wiki 등)를 대상으로 적용해보고 검색 품질을 평가할 계획입니다.
- PDF 파싱, 의미 단위 chunk 분할, Hybrid Search(키워드+벡터) 등의 개선을 통해 실용성을 높이고자 합니다.
- 팀 내 문서 기반 Q&A 도구로 발전시켜, 신규 팀원 온보딩이나 장애 대응 시 활용하는 방안을 검토 중입니다.
- [사용자 확인 후 보완] 실제 사내 문서 적용 시의 보안 및 데이터 관리 정책에 대한 검토가 추가로 필요합니다.
