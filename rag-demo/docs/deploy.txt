====================================
배포 가이드 (Deployment Guide)
====================================

1. 배포 전 점검 항목
------------------------------------

배포를 진행하기 전에 반드시 아래 항목을 확인합니다.

[코드 점검]
- 모든 PR이 리뷰 완료되었는지 확인
- CI/CD 파이프라인의 모든 테스트가 통과했는지 확인
- lint 오류가 없는지 확인
- main 브랜치에 최신 코드가 머지되었는지 확인

[환경 설정 점검]
- .env 파일의 환경 변수가 운영 환경에 맞게 설정되었는지 확인
- DATABASE_URL이 운영 DB를 가리키는지 확인
- REDIS_URL이 운영 Redis를 가리키는지 확인
- SECRET_KEY가 운영용 키로 설정되었는지 확인
- CORS_ORIGINS에 운영 도메인이 포함되었는지 확인

[인프라 점검]
- 서버 디스크 용량이 충분한지 확인 (최소 20% 여유)
- 데이터베이스 백업이 완료되었는지 확인
- 로드밸런서 상태 확인
- SSL 인증서 만료일 확인

[커뮤니케이션]
- 배포 일정을 팀 Slack 채널에 공유
- 관련 팀(QA, 운영)에 배포 사전 공지
- 긴급 연락망 확인

2. 배포 순서
------------------------------------

아래 순서대로 배포를 진행합니다.

Step 1: 데이터베이스 마이그레이션
  - alembic upgrade head 명령 실행
  - 마이그레이션 적용 결과 확인
  - 테이블 구조 변경 사항이 있으면 DBA에게 사전 리뷰 요청

Step 2: 백엔드 배포
  - Docker 이미지 빌드: docker build -t backend:latest .
  - 이미지를 레지스트리에 푸시: docker push registry.example.com/backend:latest
  - Kubernetes 디플로이먼트 업데이트: kubectl set image deployment/backend backend=registry.example.com/backend:latest
  - 롤링 업데이트 상태 확인: kubectl rollout status deployment/backend
  - 헬스체크 엔드포인트 확인: curl https://api.example.com/health

Step 3: 워커 배포
  - 워커 Docker 이미지 빌드 및 푸시
  - 워커 디플로이먼트 업데이트
  - Flower 대시보드에서 워커 상태 확인
  - 큐에 적체된 태스크가 없는지 확인

Step 4: 프론트엔드 배포
  - npm run build 명령으로 빌드
  - 빌드된 정적 파일을 CDN에 업로드
  - Nginx 설정 리로드: sudo nginx -s reload
  - 브라우저에서 캐시 무효화 확인 (버전 해시 확인)

Step 5: 배포 후 확인
  - 전체 시스템 헬스체크 수행
  - 주요 기능 스모크 테스트 수행
  - 에러 로그 모니터링 (Sentry, Kibana)
  - 응답 시간 모니터링 (Grafana)
  - 배포 완료를 팀 Slack 채널에 공유

3. 롤백 절차
------------------------------------

배포 후 문제가 발생했을 때 아래 절차로 롤백합니다.

[긴급 롤백 기준]
- 500 에러 비율이 5%를 초과할 때
- 주요 API 응답 시간이 평소 대비 3배 이상 증가할 때
- 결제, 인증 등 핵심 기능이 동작하지 않을 때

[백엔드 롤백]
  1. 이전 버전 확인: kubectl rollout history deployment/backend
  2. 롤백 실행: kubectl rollout undo deployment/backend
  3. 롤백 완료 확인: kubectl rollout status deployment/backend
  4. 헬스체크 엔드포인트 확인

[프론트엔드 롤백]
  1. CDN에서 이전 버전의 빌드 파일을 복원
  2. Nginx 캐시 퍼지
  3. 브라우저에서 동작 확인

[데이터베이스 롤백]
  1. 마이그레이션 다운그레이드: alembic downgrade -1
  2. 필요한 경우 백업에서 데이터 복원
  3. 주의: 데이터 손실이 발생할 수 있으므로 DBA와 협의 후 진행

[롤백 후 조치]
  - 장애 원인 분석 및 포스트모템 작성
  - 수정 후 스테이징 환경에서 충분히 검증
  - 재배포 일정 수립

4. 핫픽스 배포
------------------------------------

긴급한 버그 수정이 필요한 경우 핫픽스 배포를 진행합니다.

  1. main 브랜치에서 hotfix 브랜치를 생성: git checkout -b hotfix/이슈번호
  2. 수정 사항 커밋
  3. 코드 리뷰 (최소 1명)
  4. CI 테스트 통과 확인
  5. main에 머지 후 즉시 배포
  6. 배포 후 모니터링 강화 (최소 30분)

5. 배포 주기 및 정책
------------------------------------

- 정기 배포: 매주 화요일, 목요일 오후 2시
- 긴급 배포(핫픽스): 필요 시 수시
- 배포 동결 기간: 금요일 오후 4시 이후 ~ 월요일 오전 10시
- 대규모 변경: 별도 배포 윈도우 확보 후 진행
- 배포 담당자는 배포 후 최소 1시간 동안 모니터링에 참여
